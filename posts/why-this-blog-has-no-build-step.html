Why this blog has no build step

A static site, hand-written HTML, and a deliberate trade: fewer moving parts in exchange for a little manual upkeep.

November 6, 2026 / 5 min read Craft

Every blog begins with a stack decision, and most of them are reasonable. A static site generator, a hosted platform, or a framework with content support will all get the words online. This blog chose the least fashionable option: plain files, edited by hand, served as they are.

That decision was not nostalgia. It was a trade with a specific constraint: the site should be understandable end to end by one person, and it should still work if every dependency in the world changed tomorrow.

What “no build step” means

There is no package manager, no bundler, no template engine, and no generated output. The repository contains the site. What you see in the file tree is what the browser receives:

  • index.html lists the posts and introduces the blog.
  • about.html and 404.html cover the static pages.
  • posts/ holds one HTML file per post.
  • assets/ holds one stylesheet, one small script, and a favicon.

Serving it locally is a single command:

python3 -m http.server 8000

Publishing is the same story. Any static host can serve the directory. GitHub Pages, a bucket, or a small VPS with a file server will all produce the same result because there is nothing to compile.

What we give up

“No build step” is not a free win. It trades automation for directness, and the cost shows up in a few places.

Manual indexes. Adding a post means editing the list on the home page and the navigation links between posts. A generator would do that from front matter. Here it is a deliberate copy, which also means a typo is always one review away.

Repeated markup. Every page carries its own header and footer. That is more HTML to keep consistent, and it is why the shared pieces are intentionally small. When duplication starts to hurt, it is a signal to add a build step, not to add a component framework.

No content tooling. There is no Markdown pipeline, no scheduled publishing, and no editorial dashboard. Writing happens in the same editor as the code. For a small publication, that is acceptable. For a newsroom, it would not be.

Manual feeds. There is no generated RSS or sitemap yet. Those can be hand-written, but they are exactly the kind of bookkeeping that automation does better. If the archive grows, that may be the first thing to automate.

Why it is still worth it

The upside is not just fewer dependencies. It is a shorter distance between what is in the repository and what a reader experiences. There is no generated file to forget to commit, no version skew between a template and its output, and no lockfile to audit. A security review starts and ends with the files you can see.

It is also fast in the way that matters for reading. The entire site is a few text files, with no external fonts and no images beyond the favicon. There are no analytics and no third-party scripts. The page loads, and then it is done.

And it is portable in a way that hosted platforms are not. The site is a folder. Moving it is a copy. Archiving it is a zip. Ten years from now, the technology required to read it will be a browser and a text editor.

When we would change our mind

A constraint is useful only if it has an exit condition. This one would be worth revisiting if any of the following became true:

  • The archive grows past a few dozen posts and the manual index becomes error-prone.
  • Publishing needs a feed, search, or tagging that would require hand-maintained duplication.
  • More than one person edits regularly and the repeated markup becomes a source of conflicts.
  • The site needs behavior that is genuinely complex, rather than occasionally interactive.

Those are not hypothetical forever. They are triggers. Until one of them fires, the simpler system is doing its job.

The point

There is a version of this decision that is just minimalism for its own sake. That is not the argument here. The argument is that the blog’s job is to publish writing, and every layer between the writing and the reader has to earn its keep.

Right now, the layers are: a text editor, a browser, and a file server. That is enough. If the blog grows into something that needs more, the stack should grow with it — deliberately, and with a reason that can be written down.

Choose the simplest system that can carry the work, and write down what would make you change it.
